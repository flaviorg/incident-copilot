# Threat model

Scope: v1 runs on the user's machine. The API listens only on `127.0.0.1` by default, MCP speaks over stdio and the War Room is static, with no backend. There is no real infrastructure: every action runs against the simulated world (`src/infra/simulated-infra.ts`). Since 0.4 the API can also receive provider webhooks and read provider data (spec 008); live incidents run in shadow mode, so nothing executes either. The section [Inbound webhooks and connectors](#inbound-webhooks-and-connectors-04) covers that surface. Since 0.5 an optional code fixer (spec 009) runs model-written code in a sandbox on the host and, after a human approval, opens a draft pull request on GitHub: the copilot's first real-world write. The section [Code fixer](#code-fixer-05) covers those two trust boundaries. Even so, the project treats everything that comes from outside the code as untrusted. That includes the model itself.

Principle: **no defense depends on the prompt.** The prompt delimits and marks untrusted data, and that helps. But the guarantee comes from the code: a deny-by-default catalog, a tier computed without reading the LLM output, no executor for tier 4, an approval state machine and redaction on every output.

## Secrets

`APPROVAL_TOKEN` and `OPENROUTER_API_KEY` go through `redactSecrets` when set and at least 8 characters long. Every secret resolved from `copilot.yaml` joins them, including `GITHUB_FIX_TOKEN` (0.5). Redaction applies to all text leaving the process:

- HTTP responses (`onSend` hook);
- MCP content;
- trace (`TraceSink`);
- audit (`appendAudit`);
- stderr logger;
- reports in `reports/`;
- War Room recordings.

`secrets.e2e.test.ts` sets both secrets, approves through the API with the token pasted in the comment and scans all 7 surfaces. The War Room recorder creates its own containers, with a random token and without inheriting `process.env`; so the test records with the key in `process.env` and also scans the recording for the tokens the recorder actually used in the decisions (`recordScenarioWithTokens`). The expected result is zero matches.

In the repository, `scripts/check-secrets.ts` (`npm run check:secrets`, also in the pre-commit and in CI) looks for keys shaped like OpenRouter or OpenAI keys and for `APPROVAL_TOKEN=` assignments with a value. It prints only the path and line, never the value found. The local `.env`, which is in `.gitignore` and is where the README says to put the real key, stays out of the scan; if Git tracks it (`git ls-files`), it is scanned again and blocks the commit. `.env.example` is always scanned (`check-secrets.unit.test.ts`, "a gitignored local .env is skipped, .env.example is still scanned" and "a local .env tracked by Git is scanned and reported").

## Inbound webhooks and connectors (0.4)

Live mode adds two surfaces: `POST /ingest/:connectorId` (and `/ingest/:connectorId/:token`), which providers call, and the read-only query calls the connectors make to provider APIs. Design: [`docs/connectors-architecture.md`](connectors-architecture.md); acceptance criteria AC-42 to AC-59 in [`specs/008-connectors/spec.md`](../specs/008-connectors/spec.md).

| Threat | Defense | Test |
|---|---|---|
| **Spoofing** a provider (a forged alert opens an incident and spends LLM budget) | `/ingest/*` is exempt from `API_TOKEN` but every connector must declare its own authentication; the config loader refuses an ingest block without it. Sentry: HMAC-SHA256 of the raw bytes with the integration's Client Secret (`Sentry-Hook-Signature`), checked before `JSON.parse`. Generic webhook: HMAC, Bearer, Basic, a custom header or a URL token. Bugsnag sends no signature or secret header, so it uses a secret URL token (`/ingest/<id>/<token>`, 24 to 128 path-safe characters) and an optional IP allowlist. Alertmanager and New Relic: Bearer, Basic or a custom header. The IP allowlist reads the address Fastify reports, and `ingest.trustProxy` is `false`, a hop count or a list of proxy addresses, never plain `true` (which would trust a client-written `X-Forwarded-For`). Every comparison is constant-time; a failure is 401 `invalid_webhook_credentials` with a generic message and nothing recorded | `connectors-auth.unit.test.ts`; `connectors-sentry.unit.test.ts` (AC-57); `connectors-bugsnag.unit.test.ts`; `ingest.e2e.test.ts` |
| **Replay** of a captured request | Idempotency on `(connectorId, externalId)`: a repeat is counted as a duplicate and changes nothing. No provider signature in 0.4 carries a verified timestamp (Sentry's `Sentry-Hook-Timestamp` is not known to be signed, so no replay window is enforced). Bugsnag's `externalId` includes the receive time, so a replayed Bugsnag body is not a duplicate; it still deduplicates into the open incident of its fingerprint inside `ingest.dedupeWindowMin`, and it needs the secret URL token in the first place | `ingest.e2e.test.ts` ("a repeated payload counts duplicates and enqueues nothing"); `alert-queue.unit.test.ts` |
| **Denial of service** | Route-level body cap (`ingest.maxBodyBytes`, default 1 MiB, 413); a token bucket per connector (`ingest.rateLimitPerMin`, default 60, 429 with `Retry-After`), spent only by requests whose credentials verified, so a flood of bad credentials cannot starve the real provider; back-pressure on the queue (`ingest.maxQueued`, default 100: 503 before anything is recorded while the queue is full, so the provider retries); graph runs share `MAX_CONCURRENT_RUNS` with `POST /incidents` | `ingest.e2e.test.ts`; `alert-queue.unit.test.ts`; `ingest-domain.unit.test.ts` (token bucket) |
| **Prompt injection** through alert titles, attributes, error messages, log lines, MCP tool descriptions and results | All inbound and queried text is sanitized (control characters removed, `<<<` and `>>>` neutralized, clipped) and reaches the LLM only as alert data or inside an untrusted observation. No tier, approval or execution decision reads it, and in shadow mode nothing executes at all. MCP tools are an explicit allowlist; a tool annotated destructive or not read-only is refused; operator-written descriptions replace the server's. The alert of a live incident (title, rule, service) is external data too: the telemetry, planner and supervisor prompts show it between the untrusted-observation markers with a notice, and it cannot close the block early | `live-incident.e2e.test.ts` (AC-50); `connectors-mcp.unit.test.ts` (AC-58); `prompts.unit.test.ts` |
| **Query injection** (NRQL and other query languages) | Queries come only from config templates; the LLM never writes a query string. That includes `query_external`: an MCP tool takes the operator's `arguments` template, the model only fills `{service}` (scope-checked) and `{window}`, and any other key is `unsafe_input` before the server is contacted. Substituted values must match a strict character allowlist, or the tool answers `unsafe_input` without sending a request | `connectors-newrelic.unit.test.ts`; `connectors-newrelic-query.unit.test.ts`; `connectors-mcp.unit.test.ts`; `tools-live.unit.test.ts` |
| **SSRF** through connector or notifier URLs | Base URLs come from `copilot.yaml` only, never from a payload or the LLM. `https` is required (plain `http` only for loopback hosts where a connector allows it); the HTTP client refuses redirects (`redirect: "error"`), has a per-call timeout and caps the response size. Path segments taken from config (project ids, slugs) are validated and URL-encoded | `copilot-config.unit.test.ts`; `connectors-http.unit.test.ts`; `connectors-sentry-query.unit.test.ts`; `connectors-bugsnag-query.unit.test.ts` |
| **Secret leakage** (webhook tokens, HMAC keys, API keys, the Slack webhook URL) | Secrets enter only as whole `${VAR}` references and join the redaction list (AC-52). `config check` and the loader report `{ path, rule }`, never a value. Connector errors carry a fixed message per `ConnectorError` kind. Outbound requests never log headers or bodies. Request URLs are redacted before they are clipped in the access log and in the 404 message, so a URL token never leaks, not even a prefix of it | `copilot-config.unit.test.ts`; `cli.e2e.test.ts` (`config check`); `ingest.e2e.test.ts` ("a secret in a long unmatched path is redacted before clipping"); each connector's conformance run |

Accepted risks in 0.4:

- **The rate limit runs before authentication.** An unauthenticated flood can drain a connector's token bucket, so the real provider gets 429 for a while (providers retry). The body cap and the bounded queue keep memory bounded.
- **Cross-provider correlation is out of scope.** One outage seen by two providers opens two incidents.
- **The queue is in process.** Queued alerts are recovered from the database on start; a run interrupted by a crash is not resumed.

## Code fixer (0.5)

The code fixer (spec [`009-code-fixer`](../specs/009-code-fixer/spec.md), guide [`docs/code-fixer.md`](code-fixer.md)) adds two trust boundaries:

1. **Model-written code runs on the host.** The test author's test file and the patch author's edits run with `node --test` inside the attempt's work tree. The repository's own code and tests run there too, and they are untrusted as well: anyone who can push to the allowlisted branch controls them.
2. **The GitHub write path.** A token with `contents: write` and `pull_requests: write` on the allowlisted repositories, used by `CodeFixPublisher` only, after a human approval bound to the patch hash.

Everything else the fixer reads (stack traces, exception messages, repository files such as `AGENTS.md`, test output) is untrusted text: sanitized, clipped, fenced in `<<<UNTRUSTED ...>>>` blocks for the model, and never used to choose a repository, path, commit, command, tier, approval or publication.

The kit preload also blocks `fetch`, `node:net`, `tls`, `dgram`, `dns`, `http`, `https`, `http2` and `child_process`, but that is best effort (Node 24.21 has no `--allow-net`). Accepted risks in 0.5:

- **The reporter runs in the test process.** Code in the same process can forge results; static bans narrow this, and the human who approves must read the diff. A pull request is evidence, not proof.
- **`best_effort` has no OS network isolation.** It is opt-in, stamped everywhere, and meant for hosts with nothing to lose.
- **Branch protection is checked only as far as the token can see.** The copilot cannot introspect a fine-grained token's scopes or confirm a ruleset it cannot read; it fails closed on `protected: false`, and scoping the token is an operator duty.
- **The repository's own suite is trusted to finish.** It runs under the same sandbox and timeout, but a hostile maintainer of the allowlisted repository controls it; allowlist only repositories whose push access you trust.

## Forbidden action: three layers

1. **Type.** The executor registry is `Record<ExecutableActionType, Executor>`, and forbidden types do not belong to `ExecutableActionType`. No code exists that executes them. A `@ts-expect-error` in `autonomy.unit.test.ts` ("forbidden types are not executable at the type level") breaks the typecheck if that changes.
2. **Gate.** `classifyAction` returns tier 4 for forbidden and unknown types, and the gate neither runs a dry run nor queues them. The action ends up `blocked_forbidden` or `blocked_unknown`, with an audit entry and a gate `critique`.
3. **Database.** The `audit_log` table has `BEFORE UPDATE` and `BEFORE DELETE` triggers that abort, and the store has no delete method (`store-audit.unit.test.ts`, "audit_log rejects UPDATE and DELETE"). Each incident has its own hash chain, starting from the genesis hash, so the trail returned by `GET /incidents/:id/audit` verifies on its own even with interleaved incidents ("each incident trail is its own chain, verifiable from genesis even when incidents interleave").

## Accepted risks in v1

- **Single token.** There are no users or roles (no RBAC).
- **In-memory protections.** The breaker, the execution limiter and the token-attempt lockout live in memory, per process. Restarting the API resets all three.
- **Global token lockout, not per client.** There is one `TokenAttemptLimiter` per process, and it also counts requests without a token. Any local client that gets the token wrong or forgets it 5 times in 10 min locks every decision for 10 min, including those from the operator with the right token (429 `approvals_locked`). It is a simple denial-of-service path for the approval flow, accepted because the API only listens on `127.0.0.1`. Way out in v2: key attempts by remote address or by session.
- **Expiry without a scheduler.** An incident whose operator never tries to decide stays `awaiting_approval` in the database, even though reads show the approval as `expired`.
- **No per-client HTTP rate limit.** The API only listens on `127.0.0.1`. Since the November 2026 review, `MAX_CONCURRENT_RUNS` (default 2) caps the runs started at the same time, the `Host` header must be a loopback name, `HOST` or one of `ALLOWED_HOSTS` (421 otherwise, against DNS rebinding), and a write with a cross-site `Origin` gets 403. With `API_TOKEN` set, every route except `GET /health` needs `Authorization: Bearer`, compared in constant time; `npm start` refuses a non-loopback `HOST` without it. A wrong API token has no lockout (unlike the approval token), so pick a long random value.
- **Run interrupted by a process crash.** The guard against decisions during a run reads `runs`. A row with no end that this process is not running, and that started more than `RUN_TIMEOUT_MS` + 60 s ago, belongs to a crashed process: it is closed with outcome `abandoned` (log event `run_abandoned`) and decisions go through again. A resume whose run failed can be retried with `POST /incidents/:id/resume`. The blackboard is the one saved before the crash, so the crashed run's partial work is lost.
- **Injection in real mode.** Delimited text in the prompt does not stop the model from proposing something bad; only the catalog and the gate stop execution. With a real model, a poisoned plan can still produce legitimate but useless steps (noise), which a human has to reject at tier 3.
