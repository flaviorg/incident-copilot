# Threat model

Scope: v1 runs on the user's machine. The API listens only on `127.0.0.1`, MCP speaks over stdio and the War Room is static, with no backend. There is no real infrastructure: every action runs against the simulated world (`src/infra/simulated-infra.ts`). Even so, the project treats everything that comes from outside the code as untrusted. That includes the model itself.

Principle: **no defense depends on the prompt.** The prompt delimits and marks untrusted data, and that helps. But the guarantee comes from the code: a deny-by-default catalog, a tier computed without reading the LLM output, no executor for tier 4, an approval state machine and redaction on every output.

## Secrets

`APPROVAL_TOKEN` and `OPENROUTER_API_KEY` go through `redactSecrets` when set and at least 8 characters long. Redaction applies to all text leaving the process:

- HTTP responses (`onSend` hook);
- MCP content;
- trace (`TraceSink`);
- audit (`appendAudit`);
- stderr logger;
- reports in `reports/`;
- War Room recordings.

`secrets.e2e.test.ts` sets both secrets, approves through the API with the token pasted in the comment and scans all 7 surfaces. The War Room recorder creates its own containers, with a random token and without inheriting `process.env`; so the test records with the key in `process.env` and also scans the recording for the tokens the recorder actually used in the decisions (`recordScenarioWithTokens`). The expected result is zero matches.

In the repository, `scripts/check-secrets.ts` (`npm run check:secrets`, also in the pre-commit and in CI) looks for keys shaped like OpenRouter or OpenAI keys and for `APPROVAL_TOKEN=` assignments with a value. It prints only the path and line, never the value found. The local `.env`, which is in `.gitignore` and is where the README says to put the real key, stays out of the scan; if Git tracks it (`git ls-files`), it is scanned again and blocks the commit. `.env.example` is always scanned (`check-secrets.unit.test.ts`, "a gitignored local .env is skipped, .env.example is still scanned" and "a local .env tracked by Git is scanned and reported").

## Forbidden action: three layers

1. **Type.** The executor registry is `Record<ExecutableActionType, Executor>`, and forbidden types do not belong to `ExecutableActionType`. No code exists that executes them. A `@ts-expect-error` in `autonomy.unit.test.ts` ("forbidden types are not executable at the type level") breaks the typecheck if that changes.
2. **Gate.** `classifyAction` returns tier 4 for forbidden and unknown types, and the gate neither runs a dry run nor queues them. The action ends up `blocked_forbidden` or `blocked_unknown`, with an audit entry and a gate `critique`.
3. **Database.** The `audit_log` table has `BEFORE UPDATE` and `BEFORE DELETE` triggers that abort, and the store has no delete method (`store-audit.unit.test.ts`, "audit_log rejects UPDATE and DELETE"). Each incident has its own hash chain, starting from the genesis hash, so the trail returned by `GET /incidents/:id/audit` verifies on its own even with interleaved incidents ("each incident trail is its own chain, verifiable from genesis even when incidents interleave").

## Accepted risks in v1

- **Single token.** There are no users or roles (no RBAC).
- **In-memory protections.** The breaker, the execution limiter and the token-attempt lockout live in memory, per process. Restarting the API resets all three.
- **Global token lockout, not per client.** There is one `TokenAttemptLimiter` per process, and it also counts requests without a token. Any local client that gets the token wrong or forgets it 5 times in 10 min locks every decision for 10 min, including those from the operator with the right token (429 `approvals_locked`). It is a simple denial-of-service path for the approval flow, accepted because the API only listens on `127.0.0.1`. Way out in v2: key attempts by remote address or by session.
- **Expiry without a scheduler.** An incident whose operator never tries to decide stays `awaiting_approval` in the database, even though reads show the approval as `expired`.
- **No HTTP rate limit.** The API only listens on `127.0.0.1`.
- **Run interrupted by a process crash.** The guard against decisions during a run reads `runs`. If the process crashes mid-run, the row is left without an end and the incident starts refusing decisions (409 `incident_not_accepting`). No recovery command in v1; that incident's blackboard would be stale anyway.
- **Injection in real mode.** Delimited text in the prompt does not stop the model from proposing something bad; only the catalog and the gate stop execution. With a real model, a poisoned plan can still produce legitimate but useless steps (noise), which a human has to reject at tier 3.
