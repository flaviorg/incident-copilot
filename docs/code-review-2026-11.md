## Correctness

### A half-open circuit breaker can stay blocked until the process restarts

- **Severity:** high · **Status:** fixed in 0.2.0 (the whole batch is the half-open trial; `CircuitBreaker.releaseTrial()` hands back a trial that ended without an outcome; 5 regression tests in `guards.unit.test.ts` and `nodes-execution.unit.test.ts`) · **Where:** [`src/domain/guards/circuit-breaker.ts:26`](../src/domain/guards/circuit-breaker.ts#L26)
- **Scenario:** canExecute() sets trialTaken=true. After that, only recordSuccess() (called only by the verifier) or recordFailure() can reset it. In executor-node.ts:91-107 the breaker is checked before the rate limiter. Case (a): the breaker is half_open, action 1 takes the trial, then limiter.tryAcquire rejects it as 'repeat' or 'global', so the action becomes 'throttled' and no outcome is recorded. Case (b): the breaker is half_open and the plan follows the pattern the auditor requires: create_volume_snapshot (tier 2, does not mitigate) as step 1, then delete_volume depending on it. The snapshot takes the trial and succeeds, and delete_volume gets blocked_circuit_open. No mitigating action succeeded, so afterExecutor escalates with circuit_open and the verifier never runs. In both cases openedAtMs stays set and trialTaken stays true, so state() returns half_open forever and canExecute() returns false forever. Every later execution in the process, for every incident, ends as blocked_circuit_open until a restart.
- **Suggested fix:** Check the rate limiter before breaker.canExecute(), or add breaker.releaseTrial() for trials that end without an outcome. Treat the whole batch as the half-open trial: call recordSuccess or recordFailure at the end of the executor when the verifier will not run. Alternatively, reopen the breaker with a fresh cooldown when a trial ends without an outcome so it can expire. Add a unit test where a half-open trial is followed by a throttle, and one where the trial runs a step that does not mitigate.

### applyDecision resumes without recording overdue sibling approvals as expired

- **Severity:** medium · **Status:** fixed in 0.2.0 (`applyDecision` runs the shared `expireOverdue` helper in the same transaction before counting pending approvals; e2e test in `gate.e2e.test.ts`) · **Where:** [`src/app/incident-service.ts:163`](../src/app/incident-service.ts#L163)
- **Scenario:** The gate creates approvals A1 and A2 for steps that both mitigate. A2's TTL passes and nobody records that. The human then approves A1 before its own TTL ends. pendingCount uses effectiveStatus, so A2 counts as expired and pendingLeft is 0. The phase becomes 'resume' and the executor runs. A2 is never actually expired: its row stays status='pending' with no decidedAt or decisionSource, there is no approval_expired audit entry, and its action stays 'awaiting_approval' instead of 'expired'. Its dependents are not cancelled in the cascade. If A1's action then fails or gets throttled, executorEscalationReason looks for status 'expired', does not find it, and reports no_executable_actions instead of mitigation_rejected. The post-mortem timeline also shows A2 as never decided.
- **Suggested fix:** In applyDecision, inside the same transaction and before pendingCount, record every overdue pending approval of the incident as expired. Move the loop body of expireDueApprovals into a private helper so both paths share it, including setting actions to expired, cancelDependents and the approval_expired audit entry.

### A timeout escalation after the gate leaves live pending approvals on an escalated incident

- **Severity:** medium · **Status:** fixed in 0.2.0 (the stop path closes every pending approval as expired with the cause in the audit and cancels its action, falling back to the stored action when the abort lands mid-superstep; `applyDecision` refuses escalated or resolved incidents; e2e test in `gate.e2e.test.ts`) · **Where:** [`src/app/incident-service.ts:434`](../src/app/incident-service.ts#L434)
- **Scenario:** The deadline is checked after each state the graph emits (line 420). When a run with a real LLM goes past runTimeoutMs, the timeout can trigger right after the gate state, which already wrote pending approvals to the store. The timeout path runs the escalation and reporter nodes on that state, and the incident is persisted as 'escalated'. The approvals stay 'pending', and ApprovalService.list('pending') and the War Room show them. When a human approves one, applyDecision marks the action 'approved' and adds an approval_approved audit entry. The phase is 'reporting', not 'awaiting_approval', so it never becomes 'resume'. The action never runs, but the audit trail says a human approved it.
- **Suggested fix:** When the stop path (recursion_limit or timeout) runs, close every pending approval of the incident in the persist transaction, either as expired or rejected by the system with an audit entry, and cancel their actions. Also make applyDecision and expireDueApprovals refuse with incident_not_accepting when the incident is escalated or resolved.

### A failed or crashed resume leaves the incident stuck for good

- **Severity:** low · **Status:** open · **Where:** [`src/app/incident-service.ts:176`](../src/app/incident-service.ts#L176)
- **Scenario:** (a) A resume run throws, for example a version_conflict on the final save, a fixture error or a defect. failRun closes the runs row, but the blackboard keeps phase 'resume'. That phase was saved by applyDecision. resumeIfReady (approval-service.ts:126) is the only thing that triggers resume(), and it only runs from decide() on an approval that is still pending. Every approval is already decided, so decide returns 409 approval_not_pending. The incident stays 'mitigating' forever with no way to retry. (b) The process crashes or is killed during any run. The runs row keeps endedAt=null, and requireNoRunInProgress then refuses every later decision and expiry for that incident with incident_not_accepting, permanently.
- **Suggested fix:** Give a run a lease: treat runs with endedAt null and startedAt older than runTimeoutMs plus a margin as abandoned, and close them on startup or on read. Add a resume path that can be retried, through an endpoint or by letting decide/get call resume when phase === 'resume' and no run is in progress.

### The verifier hides failed reverts after a failed canary

- **Severity:** low · **Status:** open · **Where:** [`src/graph/nodes/verifier-node.ts:67`](../src/graph/nodes/verifier-node.ts#L67)
- **Scenario:** The canary fails. The verifier reverts the actions that can be reverted, in reverse order. When infra.revert returns ok:false, the action stays status 'succeeded' and is not persisted. No audit entry records the failure, and only a trace observation shows it. The canary_rollback audit lists only revertedActionIds. The escalation detail says 'reverted in reverse order: X' for the actions that worked, or 'nothing to revert'. The on-call human reads that the rollback was done while the world still has a change that did not work.
- **Suggested fix:** When a revert fails, set a resultSummary (or a dedicated status such as revert_failed), persist the action, and add revertFailedActionIds to the canary_rollback audit details. Mention the failed reverts in escalation.detail, for example 'revert of X FAILED: <summary>'.

### Duplicate step orders are accepted and make dependsOn resolution ambiguous

- **Severity:** low · **Status:** open · **Where:** [`src/contracts/plan.ts:4`](../src/contracts/plan.ts#L4)
- **Scenario:** Neither PlanStepSchema nor the auditor rules require unique 'order' values. Example: the LLM plan has two steps with order 1, A (blocked_forbidden) and B (awaiting_approval), and step 2 has dependsOn [1]. The gate (gate-node.ts:67), the executor (executor-node.ts:81) and cancelDependents (incident-service.ts:213) each resolve a dependency with find(order === n), which takes whichever step comes first. Depending on array order, step 2 can be cancelled wrongly, or can pass the dependency check while depending on a blocked step. Rejecting B also cancels every step that depends on order 1.
- **Suggested fix:** Add a refine to RemediationPlanSchema requiring unique orders, or add an auditor rule 'unique_orders' that fails the plan when orders repeat.

## Security

### LLM- or MCP-supplied runbookRef is never validated, so it decides whether a step is raised to tier 3

- **Severity:** medium · **Status:** fixed in 0.2.0 (`ClassificationContext.knownRunbookRefs`, built with `runbookRefsOf` from the retrieved matches in the gate and in MCP proposals; an unknown ref raises to tier 3 with the reason "runbook reference not among the retrieved runbooks"; unit and MCP e2e tests) · **Where:** [`src/domain/autonomy/catalog.ts:147`](../src/domain/autonomy/catalog.ts#L147)
- **Scenario:** classifyAction raises the tier to 3 only when runbookRef === null. Nothing ever checks that ref. The planner's PlanStep.runbookRef is `z.string().nullable()` in src/contracts/plan.ts:9, and gate-node.ts:47 passes the step straight in. The MCP input accepts any string up to 120 characters (contracts/api.ts:139, incident-service.ts:253). Example: the runbook retriever refuses (no runbook above the threshold, so state.runbookMatches is empty), but an injected or hallucinating planner emits runbookRef: "anything#x" on block_image_tag or tag_resource_for_review. The step keeps catalog tier 2, becomes `ready` and runs in the batch with no human approval. An MCP client can do the same by passing runbookRef: "x". This breaks AGENTS.md ('Never read a tier ... from LLM output') and constitution 1 and 5: free LLM text decides whether the no_runbook raise applies.
- **Suggested fix:** Treat runbookRef as evidence that must be checked. Add `knownRunbookRefs: ReadonlySet<string>` to ClassificationContext. In the gate, build it from state.runbookMatches (`${runbookId}#${section}`). In proposeExternalAction, build it from blackboard.runbookMatches or the RunbookRepository. Raise to tier 3 with REASONS.noRunbook when the ref is null OR not in the set. Add a unit test: an unknown ref with no matches must give tier 3.

### No Host/Origin check and no auth on mutating routes: DNS rebinding can drive the API

- **Severity:** low · **Status:** open · **Where:** [`src/http/server.ts:29`](../src/http/server.ts#L29)
- **Scenario:** The API binds 127.0.0.1 by default but never validates the Host header, and POST /incidents, GET /incidents/:id/audit, /trace and so on need no credential. A malicious page the operator visits can DNS-rebind its domain to 127.0.0.1:3000 and then make same-origin JSON requests. It can (a) POST /incidents repeatedly: each call runs the full graph against OpenRouter, costing real money with no rate limit; (b) read every incident, trace and audit; (c) trip the global approval lockout above. With HOST=0.0.0.0 (for example in a container), this is reachable from the network without rebinding.
- **Suggested fix:** Add an onRequest hook that rejects requests whose Host is not in an allowlist (127.0.0.1:PORT, localhost:PORT, [::1]:PORT, plus configured names), and rejects a cross-site Origin on non-GET requests. Add a per-client rate limit or a concurrency cap on POST /incidents. Consider an optional API token for mutating routes when HOST is not loopback.

### Text is truncated before redaction in logs and MCP output, so a secret's prefix can leak

- **Severity:** low · **Status:** open · **Where:** [`src/http/server.ts:46`](../src/http/server.ts#L46)
- **Scenario:** server.ts:46 and mcp/tool-result.ts:44 clip err.message to 500 characters, and only afterwards does the logger call redactSecrets. tool-result.ts:19 and :49 also clip before redacting. If a secret straddles the cut (for example an upstream message that echoes the key at offset 480), the clipped string holds only part of it. The literal match in redactString fails, and that prefix (for example 'sk-or-v1-' plus the next characters) is written to stderr logs or MCP content. trace-sink.ts:76 already does this in the correct order.
- **Suggested fix:** Always redact before clipping: `clipText(redactSecrets(e.message, c.secrets), 500)` in server.ts, and `clip(redactSecrets(text, c.secrets), N)` in tool-result.ts. Add a unit test with a secret placed across the clip boundary.

### HTTP redaction runs on the serialized JSON, so a secret containing JSON-escaped characters is not matched

- **Severity:** low · **Status:** open · **Where:** [`src/http/server.ts:31`](../src/http/server.ts#L31)
- **Scenario:** The onSend hook calls redactSecrets on the already-serialized payload string. If APPROVAL_TOKEN contains a character that JSON.stringify escapes (`"`, `\` or a control character), for example a password-manager token like `Ab3"x9...`, any reflection of it appears in the body as `Ab3\"x9...`. The literal match fails and the token is returned. Config only requires a length of 16 or more, with no charset limit.
- **Suggested fix:** Redact the object before it is serialized (a preSerialization hook that calls redactSecrets on the payload object), and keep onSend for string/markdown bodies. Alternatively, also redact each secret's JSON-escaped form (`JSON.stringify(s).slice(1, -1)`). Or restrict APPROVAL_TOKEN to a URL-safe charset in config.ts.

## LLM and resilience

### Real-provider cost is always 0: model-prices.json is empty and unknown models silently cost 0

- **Severity:** medium · **Status:** fixed in 0.2.0, partly (no longer silent: `missingPrices` plus a startup `warn` with `event: llm_price_missing`, documented in the README; the cost of an unpriced model still records as 0, and reading OpenRouter's reported cost is future work) · **Where:** [`src/llm/usage.ts:16`](../src/llm/usage.ts#L16)
- **Scenario:** data/model-prices.json ships with "models": {}. With LLM_PROVIDER=openrouter and OPENROUTER_MODEL=anthropic/claude-x, estimateCostUsd hits `if (!p) return 0`, so every llm_calls row and every incident cost total reads $0.00. This is true for the primary and the fallback model. Nothing logs or flags it, so cost dashboards and budgets look fine while real money is spent. A typo in a model id also falls back to 0 without any signal.
- **Suggested fix:** Have createLlmProvider check that the primary and fallback models both exist in prices.models when llmProvider==='openrouter', and fail config or log a loud warning at startup if not. Make estimateCostUsd return null, or carry a costKnown:false flag, for unknown models, and record it as unknown instead of 0. As an alternative, read OpenRouter's reported cost (usage.cost, via `usage: {include: true}`) rather than estimating.

### Input-schema bugs in buildUser are misclassified as server_error, retried, and sent to the fallback model

- **Severity:** low · **Status:** open · **Where:** [`src/llm/openrouter-provider.ts:79`](../src/llm/openrouter-provider.ts#L79)
- **Scenario:** Every v1 prompt's buildUser calls XInputSchema.parse(input) (e.g. src/prompts/v1/planner.ts:38), and that throws ZodError on bad input from a node. In OpenRouterProvider.generate, buildUser runs inside the try. The catch passes the error to classifyProviderError, which has no status, so it returns { kind: 'server_error', 'network or provider failure' }. resilient() then retries twice and calls the fallback, and the incident escalates as llm_unavailable while the real cause, a code defect, is hidden. FakeLlmProvider calls buildUser outside any try (fake-provider.ts:68), so the same bug throws in tests. Provider behaviour diverges, and the bug only shows in production as a fake 'outage'.
- **Suggested fix:** Build the messages (prompt.buildUser(input)) before the try, or rethrow non-provider errors (ZodError and similar) from the catch, so repository defects propagate as exceptions as provider.ts:2-3 requires. Add a unit test that buildUser throwing in OpenRouterProvider rejects instead of returning server_error.

### Retry has no backoff and retries non-retryable errors (429, 4xx auth/credit/context errors)

- **Severity:** low · **Status:** open · **Where:** [`src/llm/resilience.ts:41`](../src/llm/resilience.ts#L41)
- **Scenario:** withRetry calls run() again immediately for every non-aborted failure. Case 1: on a 429, the second attempt fires within milliseconds and almost surely hits 429 again, so the retry is wasted and adds load to an already throttled key. Case 2: classifyProviderError maps every other HTTP status (400 context-length, 401 bad key, 402 no credits, 404 unknown model) to server_error (openrouter-provider.ts:49), so a 401 makes 2 primary calls plus 1 fallback call, all doomed. Once concurrent incidents and per-node calls are counted, this becomes a small retry storm against a provider that is already refusing.
- **Suggested fix:** Add a non-retryable kind (e.g. 'client_error'/'config_error') for 4xx other than 408/429, and skip retry for it; also skip the fallback for 401/402 when the same key is used. For rate_limit and server_error, sleep with exponential backoff and jitter between attempts, honour Retry-After when present, and make the sleep abortable by ctx.signal.

### Tokens/cost of failed attempts (retries, invalid_output) are never recorded

- **Severity:** low · **Status:** open · **Where:** [`src/llm/recording-provider.ts:24`](../src/llm/recording-provider.ts#L24)
- **Scenario:** withCallRecording wraps resilient(), so it sees one logical result. Say the primary model returns schema-invalid JSON twice (billed both times) and the fallback then succeeds: llm_calls gets one row with only the fallback's tokens. If all attempts fail, the row has promptTokens=0, completionTokens=0, costUsd=0. On top of that, OpenRouterProvider drops res.raw.usage_metadata when safeParse fails (openrouter-provider.ts:81-84), even though tokens were consumed. As a result, the cost per incident under-reports exactly in the degraded cases where it matters most.
- **Suggested fix:** Let LlmResult failures carry an optional usage (fill it from res.raw on invalid_output). Then either record per attempt (move withCallRecording inside resilient around each `once`) or have resilient sum the usage and cost of all attempts into the final result. Also record the attempt count and the model actually used.

### Missing usage_metadata silently becomes 0 tokens

- **Severity:** low · **Status:** open · **Where:** [`src/llm/openrouter-provider.ts:85`](../src/llm/openrouter-provider.ts#L85)
- **Scenario:** Some OpenRouter-routed providers, and some OpenAI-compatible endpoints set via LLM_BASE_URL, return no usage, or return it under a field that withStructuredOutput+includeRaw does not map into usage_metadata. Then `?? 0` records 0/0 tokens and $0 for a successful call. This cannot be told apart from a genuinely free call, so token budgets and cost reports go wrong with no warning.
- **Suggested fix:** When usage_metadata is absent, fall back to estimateTokens(system+user) and estimateTokens(JSON.stringify(parsed)), as the fake provider already does, and mark the usage as estimated (a flag column, or a log warning). As an alternative, request usage explicitly (stream_options/usage include) from OpenRouter.

### Timeout/rate-limit failures are recorded with model 'openrouter' and lose which model failed

- **Severity:** low · **Status:** open · **Where:** [`src/llm/resilience.ts:21`](../src/llm/resilience.ts#L21)
- **Scenario:** withTimeout's timeoutResult()/abortedResult() call llmFailure without a model. When the fallback times out, or both primary attempts time out with no fallback, recording-provider.ts:23 stores model = p.name = 'openrouter', not the model id. Operators cannot tell from llm_calls whether the primary or the fallback model was the one timing out, which hurts choosing or alerting on models.
- **Suggested fix:** Pass the provider's model into `once` (expose a readonly model on OpenRouterProvider, or pass it to withTimeout) and include it in timeout/aborted failures. Also record a 'usedFallback' flag.

## Repository, build and CI

### tsconfig uses moduleResolution 'bundler' although the backend runs on native Node 24 TS, so typecheck accepts imports that crash at runtime

- **Severity:** low · **Status:** open · **Where:** [`tsconfig.json:5`](../tsconfig.json#L5)
- **Scenario:** A contributor writes `import { x } from "../domain/errors"` (no .ts) or imports a directory index in src/. With module ESNext + moduleResolution bundler, `npm run typecheck` passes, but `node src/index.ts` / `npm run demo` fails with ERR_MODULE_NOT_FOUND because Node's ESM loader needs the full extension. The AGENTS rule 'relative imports with .ts' is then enforced only by convention or by e2e tests that happen to load that file.
- **Suggested fix:** Use `"module": "nodenext"` and `"moduleResolution": "nodenext"` (keep allowImportingTsExtensions, verbatimModuleSyntax and erasableSyntaxOnly). tsc then rejects extensionless relative specifiers the same way Node does. Keep the bundler setting only in web/tsconfig.json.

- **Severity:** low · **Status:** fixed in 0.2.0 · **Where:** [`web/src/App.tsx:66`](../web/src/App.tsx#L66)
- **Scenario:** While a recording is loading, `replay` is null, so ScenarioPicker stays rendered (line 96) next to 'Loading recording…'. A user clicks scenario A and then scenario B. If A's fetch resolves after B's, setReplay(createReplay(A)) overwrites B: the screen shows A although B was clicked last. `loading` also flips to false as soon as the first request finishes. If the component unmounts mid-load, setState runs on the unmounted component.
- **Suggested fix:** Keep a request token (useRef counter, or an AbortController passed to fetchImpl via init.signal) and ignore stale results: `const token = ++reqRef.current; const r = await loadRecording(...); if (token !== reqRef.current) return;`. Also hide or disable the picker while `loading` is true.

### Polite live region announces 'Event N of M · playing' every 700 ms

- **Severity:** low · **Status:** fixed in 0.2.0 · **Where:** [`web/src/components/PlaybackControls.tsx:30`](../web/src/components/PlaybackControls.tsx#L30)
- **Scenario:** During Play, the interval in App.tsx:42 advances the cursor every PLAY_INTERVAL_MS (700 ms). The aria-live='polite' status text changes on each tick, so screen readers queue a stream of 'Event 3 of 14 · playing', 'Event 4 of 14…' announcements. These drown out the content. The new conversation events themselves are never announced, because AgentConversation has no live region.
- **Suggested fix:** Announce only state changes (playing, paused, at the gate, finished) in the live region and render the counter outside it. Optionally add a separate visually-hidden live region that announces a short text for each new event, only in Step mode.

### New events are appended out of view during Play

- **Severity:** low · **Status:** fixed in 0.2.0 · **Where:** [`web/src/components/AgentConversation.tsx:88`](../web/src/components/AgentConversation.tsx#L88)
- **Scenario:** The conversation is a plain growing <ol> with no max-height and no scroll handling (components.css has no overflow on the conversation). During Play, new events and agent groups are added below the fold every 700 ms, and the controls and gate are far away. The viewer either sees nothing change or has to scroll by hand, which defeats the point of the replay.
- **Suggested fix:** Make the conversation a scroll container (max-height plus overflow-y:auto) and scroll the newest event into view (block 'nearest'; respect prefers-reduced-motion) when events.length grows. Pause auto-scroll when the user has scrolled up.

### Gate steps show contradictory status after the decision and before the branch ends

- **Severity:** low · **Status:** fixed in 0.2.0 · **Where:** [`web/src/App.tsx:137`](../web/src/App.tsx#L137)
- **Scenario:** After the user picks a branch, currentSnapshot returns common.incident.actions (still 'awaiting_approval') together with chosen.approvals (approved or rejected) until the branch finishes (replay-engine.ts:59). statusText then shows 'awaiting apr-1 (approved)' or 'awaiting apr-1 (rejected)' for every step while the branch replays, which is confusing. The header Status also stays 'replaying' even though the decision is known.
- **Suggested fix:** In statusText, when the linked approval is no longer pending, show the decision instead, e.g. `${approval.id} ${APPROVAL_STATUS_LABELS[approval.status]}`. You could also record per-event snapshots so actions and approvals stay consistent.

### Index load failure has no retry and leaves an empty dead page

- **Severity:** low · **Status:** fixed in 0.2.0 · **Where:** [`web/src/App.tsx:94`](../web/src/App.tsx#L94)
- **Scenario:** If ./demo/index.json fails (network blip, or the app is served at a path without a trailing slash so the relative URL resolves wrongly), the page shows only the alert text. There is no picker, no retry and no loading state. The user must reload the page. A failed recording load likewise offers no retry on the same card beyond clicking it again.

## Rejected by verification

These were raised by a reviewer and refuted by the verifier (already handled, unreachable, or intended by the specs). They are listed so nobody re-raises them without new evidence.

- `src/graph/nodes/executor-node.ts`: A failed execution escalates with the reason no_executable_actions. *Why rejected:* The code path can happen: scenario `faults` make `infra.execute` return ok:false. A failed mitigating action then leaves `mitigated` false, and `executorEscalationReason` falls through to `no_executable_actions`. But this behavior is intended and documented, not a defect. The priority list in the executor docstring (spec table 4.5.1) and the `executor` row in docs/architecture.md (line 127) name exactly the four reasons `circuit_open`, `throttled`, `mitigation_rejected` and `no_executable_actions`. No escalation reason exists for a failed execution, and the spec's AC-14, AC-19 and AC-20 require none. The test 'execution failure records a breaker failure' in tests/unit/nodes-execution.unit.test.ts (lines 92-102) checks the exact case, a rollback with an injected fault, and asserts `out.escalation!.reason === "no_executable_actions"`. Also, the human is not misled the way the finding claims. `escalationDetail` lists each mitigating action with its status label (for example 'rollback_deployment failed'), and the executor also records `action_failed` and `circuit_opened` audit events and an observation in the trace. The finding is at most a suggestion to add a more specific reason, not a correctness bug against the spec.
- `src/app/approval-service.ts`: Overdue approvals are only recorded as expired when someone tries to decide them. *Why rejected:* The described behavior is real, but the spec chose it on purpose. specs/004-remediation-gate/spec.md line 19 says expiration is "projected on read and materialized on decision". Line 39 lists "A scheduler that materializes expiration without a decision attempt (v2 backlog)" as out of scope. AC-15 also requires that reads "show it as expired without writing anything" and that expiration is materialized only when a decision arrives. docs/architecture.md:149 says the same: "materialized on a decision attempt". Reads already show the effective status through effectiveStatus (views.ts, ApprovalService.list, stats). The finding's suggestion to record expirations from get/list would break AC-15's rule that reads write nothing. So this is a known, documented design limit with a scheduler on the backlog, not a defect.
- `src/app/approval-service.ts`: Any unauthenticated client can lock out all approvers. *Why rejected:* The code works as the finding says: there is one TokenAttemptLimiter per process (container.ts:176), and approval-service.ts counts missing or wrong tokens before it checks anything else. But this is a known, documented, and accepted design choice. docs/threat-model.md:53 under "Accepted risks" says "Global token lockout, not per client", describes this exact denial-of-service path, accepts it because the API only listens on 127.0.0.1 (config.ts HOST default, index.ts), and names "key attempts by remote address" as the v2 way out. specs/005-http-api/spec.md:26 also leaves per-client rate limiting out of scope for the same reason. With the default bind, the attacker would have to be local. So this is not a new defect; at most it is a v2 hardening note.
- `src/app/approval-service.ts`: Global token-attempt lockout lets any unauthenticated caller block every approver. *Why rejected:* The code does behave as the finding says. TokenAttemptLimiter is one counter per process (container.ts:176). It counts requests with no token (approval-service.ts:58-59), and isLocked is checked before the token comparison (line 54). But this is intended, documented behavior, not a defect. The check order "corpo, token configurado, bloqueio, token" comes from spec 6.5, which is cited in the decide() docstring. AC-18 (specs/005-http-api/spec.md:35) requires a global 429 after 5 wrong attempts in 10 min. docs/threat-model.md:53 names the exact DoS path and accepts it, including requests without a token and an operator with the right token being locked out. It plans "key attempts by remote address" for v2. README.md:537 says the same. The exposure is limited to 127.0.0.1 (spec 005, src/index.ts). Whether an attacker can reach the endpoint at all depends on a separate DNS-rebinding finding. On its own, this is a known accepted risk, not a new bug.
- `src/app/incident-service.ts`: MCP proposals skip the deterministic auditor rules and dry-run against the base world, not the accumulated plan. *Why rejected:* This behavior is intended by the spec, not a gate bypass. specs/006-mcp-server/spec.md says proposeExternalAction "classifies the action, validates parameters and runs the dry run on the blackboard's world", and that is what line 276 does. The auditor rules (runAuditorRules in src/domain/audit/auditor-rules.ts) are the auditor node's Reflection floor on an LLM-written RemediationPlan (spec 003). They are not part of the gate: gate-node.ts only classifies the action, dry-runs it on a world that carries forward each earlier step's effects, and applies it. The MCP path still does classification, catalog parameter validation and the dry run. It never executes anything. A tier 3 action such as delete_volume always creates a pending approval that a human must decide through the API. The approval records proposedBy "mcp_client" and audits the rationale, so it does not "look identical to a gate-vetted action". release_requires_unassociated is already covered by the simulated dry run, which fails when the IP is associated. The duplicate-release case would at worst end as a recorded execution failure after human approval. It does not cause unsafe execution. Not dry-running against the world with already-accepted actions applied is a real difference from the graph gate. It is a minor robustness gap that the spec explicitly allows, so it is at most a low-severity design suggestion.
- `src/app/incident-service.ts`: A crashed run leaves endedAt NULL and permanently blocks approvals and expiry for that incident. *Why rejected:* The mechanism is accurate: the row is written with endedAt null at incident-service.ts:399 and only closed on a caught error (403) or on normal completion (447). requireNoRunInProgress (line 177) then refuses applyDecision and expiry, and nothing reconciles stale runs. However, the project already documents this as an accepted v1 limitation. docs/threat-model.md:56, under "Run interrupted by a process crash", describes this exact outcome (409 incident_not_accepting), says v1 has no recovery command, and argues the incident's blackboard would be stale anyway. Because it is a known, intended trade-off and not an undiscovered defect, it does not count as a new finding. At most it is a v2 improvement suggestion.
- `src/infra/db/incident-store.ts`: The audit hash chain is unkeyed and has no external anchor, so anyone with DB write access can rewrite it. *Why rejected:* The mechanics are described correctly. appendAudit (incident-store.ts ~193-204) computes a plain sha256(prevHash + "\n" + canonicalJson(body)), and the triggers can be dropped, as addAuditSeq in schema.ts does with DROP TABLE. Even so, this is not a real defect within the project's stated scope.

docs/threat-model.md says v1 runs on the user's own machine, with the API on 127.0.0.1 only and no real infrastructure. It describes the audit protections (triggers, no delete method, a chain per incident from genesis) as layer 3 of "forbidden action". That layer defends against the app or the LLM path deleting or altering audit rows. It does not defend against someone who can already write the SQLite file. Neither the README nor the threat model claims tamper-evidence against the database owner. They only promise "insert-only" and a chain the client can recompute.

An attacker who can write the database file on that machine can also edit the code or read the environment. The proposed HMAC key would live in config or env on the same host, so it adds almost no protection there. Only the external-anchor idea would change anything, and that is a v2 hardening item.

At most, this is a missing line in the threat model's "Accepted risks in v1" section, not a reachable vulnerability.
- `src/llm/resilience.ts`: Worst-case latency per logical call is 3x LLM_TIMEOUT_MS with no shared per-call deadline. *Why rejected:* The arithmetic is correct. resilient() in src/llm/resilience.ts:49-58 gives each attempt a fresh withTimeout(o.timeoutMs). With the defaults from src/config.ts:64-65 (30000 and 180000), one logical call can take up to 90 s (2 primary attempts plus 1 fallback). However, this is the behavior the specs ask for, not a defect. specs/002-single-agent/spec.md:19 and AC-29 require withTimeout per attempt, 2 attempts on the primary and 1 on the fallback. docs/architecture.md:104-106 says LLM_TIMEOUT_MS applies only to the per-call withTimeout timer, and that RUN_TIMEOUT_MS (an AbortSignal plus a clock check on each superstep) is the overall ceiling. specs/005-http-api AC-30 sets the run-overrun outcome to escalated/timeout with a 504. When a run times out partway through the LLM chain, that outcome is the specified one, not a hidden bug. Nothing is unbounded: ctx.signal is passed to every attempt, so the run abort cancels the chain. The claim that this hides the provider problem is also overstated, because each attempt's failure is recorded in llm_calls. The suggestion is a reasonable design improvement (a per-logical-call budget, or skipping the retry after a timeout), but the current behavior follows the spec.
- `src/llm/prompt-hash.ts`: Prompt hash excludes buildUser template and output schema, so fixtures do not detect user-prompt or schema drift. *Why rejected:* The hash covering only version + system is a documented design choice, not something overlooked. The code comment in src/llm/prompt-hash.ts cites spec 7.2 rule 1 and says the output schema is left out. specs/002-single-agent/spec.md AC-26 defines drift as a change to the hash of `version + system`. docs/fake-provider.md says outright that "The output schema is not part of the hash". Its table also covers the scenario in the finding: when a prompt's input format or the graph flow changes, you edit the turns by hand, because the hash does not cover that. AGENTS.md says the same: the catalog enters the planner prompt as input, so the fixture hash does not change. Schema drift is caught separately: contracts.unit.test.ts validates each turn's output against outputSchema. The finding describes intended behavior, so at most it is a design suggestion, not a defect.
- `.gitignore`: .gitignore covers only `.env`, not `.env.*` variants. *Why rejected:* It's true that .gitignore lists only `.env`, but the failure scenario doesn't fit how this project works. Every script that loads env vars (cli, start, dev, mcp, test:live in package.json) uses `--env-file-if-exists=.env`. The README (line 278), .env.example and docs/fake-provider.md all tell developers to put OPENROUTER_API_KEY in `.env` specifically. No tool in the repo reads `.env.local` or `.env.live`, so a key placed there would never reach `npm run test:live`, which makes the scenario unlikely. scripts/check-secrets.ts exempts only the exact name `.env` (LOCAL_ENV_FILES at line 44). Any `.env.*` variant is therefore still scanned and flagged locally by `npm run verify` and the pre-commit hook, and in CI. Adding `.env.*` with `!.env.example` would be a reasonable general hardening step. Given the project's own conventions, though, this is a stylistic nit, not a reachable defect.
- `.githooks/pre-commit`: The pre-commit hook is opt-in and runs nothing until setup:hooks is run. *Why rejected:* The hook is opt-in on purpose, and the project documents that choice. The hook's own header says to install it only once the folder has its own Git repository. AGENTS.md and specs/constitution.md both restrict `npm run setup:hooks` to that case, and README line 415 already says to install it with `npm run setup:hooks`. CI runs `check:secrets` as a backstop, which the constitution requires. A `prepare` script that changes git config on `npm ci` would cut against the documented rule to install the hook deliberately. This is a valid DX preference at most, not a defect, and the README fix it suggests is already in place.
- `web/src/components/ApprovalGate.tsx`: Approval gate can dead-end: branches present but no pending approval leaves the replay stuck with no controls. *Why rejected:* I couldn't reach this with the project's own data, so I don't count it as a real defect. The finding is right that the schema doesn't check this rule. DemoRecordingSchema accepts `branches` set while `common.approvals` has no pending item. In that case settle() pauses at the gate, and ApprovalGate shows no buttons because it needs `pending.length > 0`. But recordings only come from the project's own recorder (src/app/demo-recorder.ts:55-56). The recorder returns `rest: null`, and so `branches: null`, unless a pending approval exists when it captures `common`. That means every recording it makes with branches also has a pending approval in `common.approvals`. demo-source.ts only loads project-owned files from ./demo/. The dead-end needs a hand-edited or corrupted recording file. A cross-field schema check would be reasonable hardening, but this is not a reachable high-severity bug.
- `web/src/data/demo-source.ts`: Recording is not checked against the requested scenario id; duplicate and invalid index ids are not checked either. *Why rejected:* This can't happen through the project's own pipeline. The demo files come only from recordAll in src/app/demo-recorder.ts. That function writes index.json from ScenarioRepository.list(), where the ids are the directory names, so they are unique and match ID_PATTERN. It then writes `${s.id}.json` from recordScenario(s.id), which gives rec.scenario.id === id (the e2e test asserts this). So a mismatched or duplicate id needs someone to hand-edit or rename the generated static files. Even then the only effect is a wrong label in a local demo. Spec AC-39 asks only for rejection of anything that fails DemoRecordingSchema, and the code does that. The suggested cross-check would be optional hardening, not a defect.
- `web/src/components/AgentConversation.tsx`: Duplicate trace event ids across common and branch are not rejected and break React keys. *Why rejected:* The described failure cannot happen with recordings this project produces. Recordings are only generated by src/app/demo-recorder.ts. Each branch runs in its own fresh :memory: DB, and trace_events has UNIQUE(incident_id, seq). seq comes from nextTraceSeq, which is MAX(seq)+1, and event ids are `${incidentId}:${seq}` (src/infra/ids.ts). The branch snapshot filters to e.seq > the last common seq, so branch ids cannot collide with common ids or with each other. The recorder also checks the common prefix is identical across both runs, and it parses the output through DemoRecordingSchema. The web app only loads its own static ./demo/*.json files, which come from that recorder. So a duplicate id needs a hand-edited or corrupted recording, and the worst result is a React key warning or misplaced <details> open state in a demo view. Adding a uniqueness refine would be hardening at most, not a fix for a reachable defect.
